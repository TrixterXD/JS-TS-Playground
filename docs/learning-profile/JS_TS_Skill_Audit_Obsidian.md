# Аудит навыков JavaScript / TypeScript и инженерного мышления

## 1. Executive Summary

### Краткий профиль

Текущий профиль лучше всего описывается не одним ярлыком вроде «junior», а как **неравномерно развитый фундаментальный уровень**.

Наиболее подтверждённая зона — JavaScript как язык работы с данными:

- значения, переменные, присваивание;
- условия и control flow;
- функции, параметры, аргументы, `return`;
- массивы и объекты;
- `map`, `filter`, `find`, `some`, `every`, `reduce`;
- callbacks и higher-order functions;
- динамический доступ к объектам;
- базовая работа со ссылками, мутациями и immutable updates;
- базовое моделирование данных через TypeScript.

В типичных задачах на преобразование данных пользователь часто способен работать на **L3 — самостоятельно**. Для некоторых хорошо закреплённых механизмов, особенно обычных операций над массивами, наблюдаются признаки **L4 — переноса навыка в новые ситуации**.

Главная зона нестабильности — не синтаксис, а **построение решения для новой составной задачи**.

Когда задача требует одновременно:

- понять несколько источников данных;
- определить порядок обработки;
- выделить промежуточное состояние;
- учесть edge cases;
- только после этого выбрать инструменты,

пользователь нередко начинает писать код раньше, чем сформирована полная модель алгоритма. В таких задачах уровень чаще находится между **L2 и L3**.

Хороший пример — задача связывания `users` и `quests`: отдельные механизмы (`reduce`, динамические ключи, `Partial`, narrowing) были знакомы, но архитектура решения «сначала создать skeleton активных пользователей → затем наполнить его данными quests» самостоятельно не возникла сразу.

С React ситуация более осторожная.

Пользователь имеет реальный опыт проекта на React/Next.js, писал компоненты, работал с props/callbacks/state-кодом и изменял существующий проект. Однако этого недостаточно, чтобы автоматически считать глубоко освоенными:

- rendering model;
- state ownership;
- derived state;
- lifecycle;
- closures в React;
- влияние identity/reference equality на rendering;
- разделение local/shared/derived state.

Поэтому React сейчас следует считать **частично практиковавшейся, но фундаментально не до конца проверенной областью**.

TypeScript развит сильнее, чем обычно бывает у человека с аналогичным фундаментом JavaScript. Пользователь способен рассуждать о union types, narrowing, indexed access, generics и utility types, но отдельные части знания пока локальны и иногда применяются раньше, чем полностью понятна runtime-механика.

### Общая самостоятельность

**Типичная знакомая JS-задача:** L3.

**Знакомый механизм в немного новой форме:** L3, иногда L4.

**Составная незнакомая задача из нескольких механизмов:** L2 → L3 после декомпозиции.

**TypeScript-моделирование средней сложности:** L2–L3.

**React fundamentals как самостоятельная система:** L1–L2 в зависимости от темы.

**Инженерная работа с существующим проектом:** примерно L2–L3.

Главный риск обучения сейчас — не недостаток количества изученных конструкций, а ситуация, когда новые абстракции начинают наслаиваться быстрее, чем формируется устойчивая причинно-следственная модель.

# 2. Evidence & Coverage

## Какие материалы были доступны

Аудит основан на доступной истории проекта «Хлебные крошки», текущем диалоге и извлечённых эпизодах из прошлых разговоров.

Особенно хорошо представлены:

- февраль 2026 — работа во время стажировки и первые попытки самостоятельной разработки;
- июль–август 2026 — массивы, объекты, методы массивов, immutable updates;
- август–сентябрь — Mechanism/SoloLvling, Git, типизация, domain logic;
- октябрь — интенсивная фундаментальная практика JS/TS;
- 17–25 октября — `Record`, `Partial`, narrowing, сложная агрегация данных, references, mutation, immutability и immutable state updates.

## Ограничения

Полный сырой лог каждого разговора недоступен одновременно.

Часть более ранней истории доступна в виде сохранённых результатов и summaries, а не полного пошагового диалога.

Поэтому там, где нельзя точно установить степень самостоятельности, оценка намеренно снижена до L0–L2.

Также архитектурные планы Mechanism и Jotai **не считаются доказательством знаний пользователя**, если они были созданы другим ИИ.

Опыт стажировки также **не считается автоматическим доказательством** владения React/TypeScript.

# 4. JavaScript Assessment

## Подтверждённо освоено

### Значения, переменные и присваивание

Пользователь понимает фундаментальный механизм:

> правая часть вычисляется → полученное значение присваивается переменной.

В задачах:

```js
let a = 10;
let b = a;
a = 20;
```

корректно предсказывал независимость primitive values.

Позже смог противопоставить это объектам:

```js
const user2 = user1;
```

и объяснить, что две переменные могут ссылаться на один объект.

Это не просто узнавание синтаксиса — присутствует причинная модель.

**Оценка: L3.**

---

## Conditions и control flow

Условия используются уверенно.

Пользователь понимает:

- boolean expression;
- порядок веток;
- `else` как оставшееся пространство;
- return как прекращение функции.

Особенно показателен boss `completeQuests`.

Первоначально алгоритм строился вокруг:

```ts
if (foundQuest && !foundQuest.completed) {
   ...
}
```

После разбора пользователь самостоятельно переписал функцию через guards:

```ts
if (!foundQuest) {
  return obj;
}

if (foundQuest.completed) {
  return obj;
}
```

и отметил существенное улучшение читаемости.

Это показывает переход от синтаксиса к работе с **control flow**.

Однако guard clauses пока только недавно сформированы и ещё не должны считаться автоматизированным навыком.

**Оценка условий: L3.**

**Early return: L2→L3.**

---

## Functions

Модель функций достаточно прочная.

Подтверждено понимание:

- parameter vs argument;
- каждый вызов получает собственные значения;
- `return` передаёт значение вызывающему коду;
- `return` завершает функцию;
- функции позволяют вынести повторяемый алгоритм.

В октябрьской практике пользователь самостоятельно реализовал higher-order function:

```ts
function runOperation(
  number: number,
  callback: (number: number) => number
): number {
  return callback(number);
}
```

Это хороший признак концептуального понимания.

**Оценка: L3.**

---

## Arrays и array methods

Это одна из наиболее сильных областей.

Пользователь не только использует стандартные методы, но вручную реализовывал упрощённые аналоги:

- `find`
- `map`
- `filter`
- `some`
- `every`
- `reduce`

Это важно, потому что позволяет отделить знание API от понимания механизма.

### `map`

Пользователь хорошо понимает:

> один входной элемент → один выходной элемент → новый массив той же длины.

Это проявилось даже в сложной задаче `users + quests`, где пользователь сам заметил, что `map` плохо подходит для получения одного общего объекта.

В текущей теме immutability самостоятельно выбрал `map` для изменения одного quest по `id`.

**Оценка: L4.**

### `find`

В августе существовала ошибочная модель: callback `find` якобы получает весь массив.

Эта модель была явно разобрана.

Сейчас пользователь уверенно применяет:

```ts
obj.quests.find((quest) => quest.id === questsID)
```

и понимает `Quest | undefined`.

Это хороший пример реального прогресса между занятиями.

**Оценка: L3.**

### `reduce`

Пользователь способен использовать accumulator разных типов:

- number;
- array;
- object;
- nested object;
- `Record`;
- группировка по dynamic key.

Самостоятельно писал generic reducer:

```ts
function reduceMySelf<T, C>(
  arr:T[],
  callback:(acc:C, cur:T)=>C,
  c:C
): C
```

Понимает модель:

> old accumulator + current → callback → new accumulator.

Но сложная задача `users + quests` показала предел:

сама механика `reduce` была понятна, а архитектура преобразования нескольких источников данных — нет.

Поэтому проблема уже находится **выше уровня reduce**.

**Оценка: L3, не L4.**

# 5. TypeScript Assessment

## Сильные стороны

TypeScript используется не только как набор аннотаций.

Пользователь умеет моделировать:

```ts
type Difficulty = "easy" | "medium" | "hard";
```

и понимает пользу ограничения пространства значений.

Использует indexed access:

```ts
Quest["difficulty"]
User["id"]
```

и способен связывать типы между структурами.

Пример из boss:

```ts
questsID: Quest1["id"]
```

Пользователь понимает, что TypeScript теперь разрешает только `"q1" | "q2" | "q3"`.

Одновременно был разобран важный нюанс:

даже если `"q3"` разрешён типом, конкретный runtime-массив теоретически может не содержать `q3`.

Это демонстрирует хорошее различение:

**type possibility ≠ runtime fact.**

---

## Narrowing

Пользователь хорошо понимает narrowing на базовом уровне.

Примеры:

```ts
if (!foundQuest) {
  return obj;
}
```

После этой проверки TypeScript знает, что ниже `foundQuest` больше не `undefined`.

Ранее работал с:

- `number | string`;
- `number | undefined`;
- optional keys;
- indexed access.

Также отдельно столкнулся с control-flow narrowing для indexed accesses.

**Оценка: L3.**

---

## Generics

Особенно хороший эпизод — самостоятельная реализация `mapMySelf`.

Пользователь понял, что:

```ts
map<T>
```

недостаточно, потому что callback может превратить `T` в другой тип.

Сам вывел необходимость второго generic:

```ts
<T, C>
```

Это сильный концептуальный показатель.

Но текущие доказательства относятся преимущественно к простым generics в функциях и коллекциях.

Нет подтверждения уверенного владения:

- generic constraints;
- conditional types;
- mapped types;
- infer;
- variance;
- сложной type compatibility.

Для Jotai это означает: базового generic-мышления достаточно для старта, но сложные generic API лучше не вводить без декомпозиции.

**Базовые generics: L3.**

**Продвинутые generics: L0.**

---

## `Record` и `Partial`

В задаче активных пользователей пользователь применял:

```ts
Partial<Record<User["id"], User["name"]>>
```

и понимал:

- `Record` описывает допустимое отображение key → value;
- `Partial` допускает отсутствие части ключей;
- чтение такого ключа требует учитывать `undefined`.

Очень важная коррекция была сделана вокруг runtime:

`Record` **не создаёт свойства объекта**.

Свойство создаёт JavaScript:

```ts
result[id] = value;
```

`Record` лишь описывает форму для TypeScript.

Эта грань теперь понята, но utility types пока ещё не полностью автоматизированы.

**Оценка: L2–L3.**

# 6. Algorithmic Thinking Assessment

Это сейчас наиболее важная область развития.

## Что получается хорошо

Пользователь способен:

- определить вход и выход;
- разбить знакомую задачу на шаги;
- вручную пройти массив;
- проследить состояние accumulator;
- связать данные через ID;
- обнаружить повторяющуюся структуру;
- после решения объяснить причинно-следственную механику.

Очень заметен рост способности объяснять код своими словами.

Например, в immutable boss пользователь корректно описал:

- нужно найти quest;
- создать новый массив;
- заменить нужный объект;
- пересоздать вложенную ветку player;
- использовать данные найденного quest для XP/title.

---

## Основная слабость

При новой составной задаче пользователь имеет тенденцию **раньше времени переходить к реализации**.

Это было явно признано самим пользователем: знакомые конструкции начали применяться автоматически, но перестала происходить полноценная декомпозиция.

В `users + quests` это проявилось как попытка сразу вложить:

```text
users.map(...)
   quests.reduce(...)
```

вместо предварительной модели результата.

Решение оказалось концептуально проще:

```text
1. создать skeleton результата из active users
2. пройти quests
3. наполнить существующие записи
```

Сложность была не в JS, а в **архитектуре алгоритма**.

---

## Инварианты и edge cases

Пока формируются.

В `completeQuests` первоначальная версия:

1. сначала выставляла `completed: true`;
2. потом находила quest;
3. теряла информацию о его предыдущем состоянии;
4. могла начислить XP повторно.

После наводящего вопроса пользователь переставил поиск до изменения.

Затем потребовалась ещё одна подсказка, чтобы отдельно проверить:

```ts
!foundQuest.completed
```

То есть edge case «quest уже завершён» не был встроен в модель сразу.

Однако пользователь быстро понял причину ошибки после демонстрации.

Это соответствует **L2–L3**.

# 7. React & State Management Readiness

## Что подтверждено

Пользователь работал с React-проектами и компонентами.

Есть реальные эпизоды:

- самостоятельная вёрстка React-компонентов во время стажировки;
- использование props/callbacks;

## Immutability

Это сейчас наиболее готовая React-related база.

В июле пользователь сначала делал новый массив через `map`, но мутировал объект внутри него.

После объяснения понял различие:

```text
новый массив ≠ новые объекты внутри массива
```

В октябре тема была разобрана заново фундаментально:

```text
reference
→ mutation
→ shallow copy
→ nested copy
→ array nested in object
→ structural sharing
→ immutable GameState update
```

Текущий boss показал способность собрать эти механизмы вместе.

При изменении:

```text
gameState.player.completedQuestsInfo
```

```text
GameState

```


## Debugging

Есть прогресс, но стабильность средняя.

Хорошие признаки:

- способен вручную трассировать данные;
- замечает различие actual / expected;
- умеет искать место, где ломается assumption;
- способен после ошибки объяснить её причину.

Характерный эпизод:

```js
console.log(arr.reduce(...), 1)
```

где `1` случайно был передан `console.log`, а не `reduce`.

На поиск проблемы ушло заметное время, потому что долго проверялась реализация функции вместо тестового вызова.

Это показывает полезный пробел:

> проверять не только implementation, но и test harness / call site / assumptions.

Также повторялись мелкие execution errors:

- `i` вместо `numbers[i]`;
- `>` вместо `<`;
- случайное `* 2` вместо square;
- `> 15` вместо `>= 15`.

Это не выглядит как концептуальное непонимание, но означает, что финальная механическая проверка кода пока нужна.

**Оценка: L2–L3.**

Пользователь сам отметил, что новая версия:

> «гораздо читабельнее и лучше».

При этом пока нет доказательства самостоятельного систематического refactoring крупного модуля.

**Оценка: L2–L3.**

## Архитектурное мышление

Есть хорошие сигналы.

Но большинство крупных архитектурных решений Mechanism принималось совместно с AI или senior guidance.

Поэтому нельзя ставить L3 только на основании качества проекта.

**Оценка: L2.**

# 9. Learning & Metacognition Profile

## Наблюдаемые факты

### 1. Лучший формат — механизм до инструмента

Наиболее успешные занятия проходили по модели:

```text
идея
→ данные
→ алгоритм
→ JavaScript
→ TypeScript
→ объяснение
```

Когда конкретный метод сообщается заранее, пользователь может решить задачу, но хуже развивается самостоятельный выбор инструмента.

Когда пользователь сначала сам определяет операцию, перенос знания значительно лучше.

---

### 2. Нужна устойчивая база до нюансов

Пользователь неоднократно отмечал, что постоянное добавление исключений и альтернатив создаёт ощущение:

> «дна нет».

Лучше работает порядок:

```text
основная модель
→ практика
→ закрепление
→ только потом ограничения и исключения
```

---

### 3. Сложная задача полезна после отдельного изучения кирпичей

Хорошо сработала модель boss fight.

Плохой boss:

> одновременно требует 4–5 незнакомых механизмов.

Результат:

- высокий cognitive load;
- трудно определить источник ошибки;
- возможно длительное избегание после занятия.

Хороший boss:

> собирает уже изученные механизмы в новую комбинацию.

Последний immutable boss именно такого типа.

---

### 4. Пользователь способен отслеживать качество собственного обучения

Очень сильный метакогнитивный эпизод — обнаружение, что тренировка сместилась:

от:

> «построить алгоритм»

к:

> «решить очередную задачу знакомыми методами».

Пользователь сам попросил вернуть алгоритмическую фазу.

Также самостоятельно сформулировал полезное различие:

> «мне трудно» vs «мне не хватает конкретного знания».

Это важный навык для самостоятельной инженерной работы.

---

### 5. При высокой неопределённости существует тенденция кодировать до полной модели

Это не психологический диагноз, а наблюдаемое поведение.

В знакомых задачах мыслительная модель часто возникает до кода.

В новых составных задачах пользователь иногда начинает экспериментировать непосредственно в коде, потому что «в голове алгоритм не выстраивается».

Это может быть полезно как exploration, но становится проблемой, если эксперимент заменяет формулирование модели.

---

### 6. Хорошо работает объяснение собственного решения

После решения пользователь часто способен очень точно своими словами объяснить:

- почему нужен `Partial`;
- почему `Record` не создаёт property;
- почему nested object всё ещё разделяет reference;
- почему нужно пересоздавать changed path;
- почему `map` подходит для замены одного элемента;
- почему early return упрощает flow.

Это один из лучших способов проверять настоящее понимание.

# 12. Recommended Teaching Approach

## Сохранять

### Сначала модель, потом API

Для новой темы:

```text
что происходит?
→ какие данные?
→ какое состояние меняется?
→ какой алгоритм?
→ JS
→ TS
```

### Одна новая концепция за раз

Не совмещать:

```text
closure + async + React rendering + atom dependency
```

в одном первом упражнении.

### Давать задачи без названия нужного метода

Если цель — научиться выбирать инструмент самостоятельно, не говорить:

> «реши через reduce».

Сначала пользователь должен определить форму результата.

### Проверять ручным trace

Особенно для:

- reference;
- reduce;
- closures;
- async;
- rendering.

### Использовать boss fights

Но boss должен комбинировать уже изученные механизмы.

После boss:

> определить «loot» — какие новые идеи выявила задача.

---

## Избегать

### Не перегружать нюансами до формирования базы

Контрпримеры полезны после того, как основная модель стабильна.

### Не исправлять каждую синтаксическую мелочь отдельной задачей

Если ошибка очевидно mechanical:

```text
> вместо <
```

достаточно указать её.

Новая задача нужна только при conceptual error.

### Не превращать TypeScript в замену пониманию JavaScript

Сначала runtime:

> что реально происходит с объектом?

Потом:

> что про это знает TypeScript?

### Не делать много однотипных drill tasks

Когда механизм понят, дополнительная сложность должна добавлять новую идею, а не ещё три поля в accumulator.

# 13. Unknowns & Validation Tasks

Ниже не учебная программа, а короткие диагностические проверки, которые позволят уточнить текущую модель.

## Scope

Дать 3 небольших фрагмента с:

- global scope;
- function scope;
- block scope;

и попросить заранее предсказать доступность переменных.

## Closure

Функция возвращает другую функцию, которая использует внешнюю переменную.

Попросить предсказать результат нескольких вызовов и объяснить, откуда берётся значение.

## Pure function

Дать две функции:

```text
одна мутирует input
вторая возвращает новый объект
```

Попросить определить различия и последствия.

## React rendering

Дать компонент с parent state и двумя children.

Попросить предсказать:

- какие функции компонентов вызываются;
- какие props меняются;
- какие object references сохраняются.

## State ownership

Дать небольшой UI:

```text
SearchInput
QuestList
QuestCounter
```

и спросить:

> где должен находиться query, quests и filteredQuests?

Без Jotai.

## Derived state

Дать:

```text
quests
completedQuestCount
```

и спросить, нужно ли хранить оба значения.

## Async

Короткий пример Promise / async function с несколькими `console.log`.

Попросить определить порядок выполнения.

## Type compatibility

Несколько типов с optional fields / unions / object widening.

Попросить определить, какие присваивания TypeScript разрешит и почему.
